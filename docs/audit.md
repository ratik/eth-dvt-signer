# Adversarial audit of the signing path

Scope: authorization safety, durable recovery, crash consistency, concurrency, partial-signature
collection, Byzantine participants, timeouts and limits, process lifecycle. Method: read the code
paths below, then reproduce every claim with a test (deterministic simulation where possible, real
processes otherwise). Passing tests are evidence, not a proof.

## 1. Trust boundaries

| Event | Where | Code |
| ----- | ----- | ---- |
| Authorization visible (in memory) | executor, inside `Store::apply_block` (holds `&mut` until `sync`) | `src/storage.rs` |
| Authorization durable | `Metadata::sync` returns | `src/storage.rs` |
| Signer learns an authorization | `Committed` values, sent after the sync, before any client answer; or read from disk at start | `src/executor.rs`, `src/dkg/actor.rs` |
| Duty decided, signing root computed | `Protection::authorize` inside `Store::apply_block`, from the typed duty of the finalized command; record and authorization in the block's one sync | `src/slashing.rs`, `src/storage.rs` |
| Signer learns a duty authorization | `(ceremony round, root)` sent after the sync, before any client answer (`AuthorizedDuties`); or `Protection::authorized_roots` read from disk at start | `src/executor.rs`, `src/engine.rs`, `src/dkg/actor.rs` |
| Partial signature generated | `dkg::actor::partial` only: local coordinator, peer request, or parked request released by `Authorized` | `src/dkg/actor.rs` |
| Signature returned | coordinator `sign`, after recovery and verification | `src/signer/coordinator.rs` |
| State restored from disk | `Store::init` (state), `Secrets::init` (shares), marshal (re-delivery from its processed height), simplex journal | |
| Messages served before catch-up | HTTP and p2p are up immediately; signing requests are refused (`not_authorized`) or parked | `src/rpc.rs`, `src/dkg/actor.rs` |
| Coordinator retries | re-sends requests to silent participants every 500 ms until the deadline; clients may repeat requests | `src/signer/coordinator.rs` |
| Allocations | in-flight counter (max 256, drop guard), response sessions (drop guard), parked queue (256, 16 blocks) | |

## 3. Remaining issues and unsupported scenarios

| ID | Issue | Impact | Evidence |
| -- | ----- | ------ | -------- |
| L-1 | **Rollback of a quorum (here: every node) to older storage is undetected.** Nothing remembers the authorization, so a conflicting payload is authorized: two valid signatures for one `(ceremony, nonce)` of the development `POST /sign`. **Narrowed for Ethereum duties (restart floor):** every keyholder process refuses a new block, attestation, PTC vote or envelope of a slot (an attestation: an epoch) it may have signed for before it started, so after a whole-network rollback the shared keyholder of any two quorums refuses the conflicting duty; no double proposal or double vote is signed ([slashing-protection.md](slashing-protection.md#the-restart-floor)). Still open: a surround vote a client crafts (honest clients never send one), the development `POST /sign`, and detection itself, which needs state outside the nodes (an external anchor; a counter in the same, rollbackable storage does not help). The floor costs the current epoch's attestations when every node restarts at once, nothing when one does. See [recovery.md](recovery.md) §7. | Safety, unsupported scenario. **Narrowed** (slashable duties); applies to imported keys unchanged | `rollback::a2_whole_network_rollback` and `eth2::e2e_eth_l1_whole_network_rollback_signs_a_double_proposal` (without the floor): both **fail**, kept `#[ignore]`; `floor::floor_1` to `floor_3` (with it) pass |
| L-2 | **Addressed.** A lagging or rolled-back node reports why it is not ready (`/status`, `/ready`: `no_block_since_start`, `local_backlog`, `no_recent_finalization`, `share_unavailable`) and refuses new authorizations (`503 NOT_READY`) instead of timing out. | L-3 | Identical requests coalesce per node only: the same request sent at once to all four nodes runs one task on each (at most four commands, four collections). Documented as an optimization: consensus alone decides what is authorized; several coordinators may aggregate the same payload. | Load, bounded by the node count | `concurrency::b1_identical_requests` (at most one command per node) |
| L-4 | **Fixed.** The parked queue was shared: one peer could evict other peers' parked requests. Now at most 64 per peer and 256 in total; a flooding peer evicts only its own. A disconnect does not release parked requests (expiry after 16 blocks does). | Latency only | `dkg::parked::tests`, `adversarial::e4_e5_parked_overflow_and_expiry` |
| L-5 | **Fixed.** A participant banned for a request still received its retransmissions. Now it is not asked again for that request (exactly one request in D4, where there were about ten). | Wasted messages | `adversarial::d4_strike_limit` |
| L-6 | No client authentication or rate limiting: any HTTP client can create authorizations and slashing records (consensus and storage cost). It can also use up a validator's slot or epoch with a duty for the wrong block or fork version, which is a liveness loss for that duty. **Narrowed (P0, P0.1, P0.2, P0.3):** it cannot record a duty whose slot or epochs have not started (the time horizon), cannot get a voluntary exit or a deposit signed, and cannot perform another protected operation (activation, imported-key registration, reshare to new keyholders, reconfiguration, EIP-3076 history import) without the approvers' offline signatures ([administration.md](administration.md)); it cannot use up a slot or epoch with another fork version, since only the pinned schedule's `fork_info` is admitted; cannot get a builder registration signed outside the approved registration policy, and its registrations wait in a bounded queue, at most 16 per block, after every other duty. Still open to it: starting DKG ceremonies, R1 refreshes, activating or aborting reshares, import dry runs, and signing other duties within slashing protection (a wrong block root still uses its slot). The API binds to loopback only, with no option to expose it. The raw signing API exists only in `dev-api` builds. | Availability | design, `tests/production_api.rs`, `admin_1` |
| L-11 | Slashing history is never pruned. It grows by ~66 bytes per authorized duty, and every block rewrites the state partition (a block with one duty: 4.1 ms on disk with no history, 10.5 ms with 50 000 records). The surround check scans the validator's attestations with a lower target (normally all of them: 341 µs with 100 000). Pruning needs EIP-3076 low watermarks (refuse at or below the pruned range). | Performance over a validator's lifetime | design; measured in §6 |
| L-12 | **Addressed (P0.3).** The validator client's `fork_info` was trusted for the fork versions (the domain). Every node now pins its network's fork schedule (`--eth-network`, or `--eth-fork-schedule` for another network) and refuses, at the API, the leader and every voter, a duty whose `fork_info` is not a fork of the schedule or gives another version than the schedule's at the duty's domain epoch (exits after Deneb: Capella's version; deposits: the genesis fork version, no root). The network's identity is bound into the cluster id and recorded with every protected command; a node started for another network refuses to start. Remaining: a keyholder cannot check the fork of an authorization finalized before P0.3; the schedule's digest is compared (`mpc-admin status`) but not enforced, so a release that adds a fork can roll out node by node; an exit's fork other than Lighthouse's `{capella, capella, exit epoch}` after Deneb is refused; only the mainnet preset is supported. | Liveness of a duty (formerly); compatibility with non-Lighthouse clients | [ethereum-signing.md](ethereum-signing.md#fork-schedule); `tests/unit/eth/network.rs`, `forks::p03_1` |
| L-13 | **Deposit signing is first come, once per key.** **Narrowed (P0.2):** a deposit is signed only with the approvers' authorization over its exact withdrawal credentials, amount and genesis fork version, checked by every voter (before P0.2, any single faulty node could bypass `--enable-deposit-signing`, which only the API checked, and take the key's one deposit message); the rest of this entry now concerns approvers. On a node started with `--enable-deposit-signing`, any client of its API obtained the key's one deposit signature, with withdrawal credentials of its choice, if nobody did before. A wrong first request (amount, credentials, genesis fork version) uses that signature for good: any other deposit message for the key is refused (`too_many_roots`). The first deposit on chain sets the credentials; later deposits to the key are top-ups to them. | Onboarding of a key; the funds of later deposits if the credentials are not the operator's | E2E-ETH-10, `slashing::tests::a_validator_signs_one_deposit_message_of_its_own_key`; mitigations: the flag is off by default and the API is loopback-only. | L-14 | **Two nodes restarted together can stall signing for seconds, enough to miss Ethereum duties.** When both missed the certificate of the view the others are in (H-8), consensus waits for the intact nodes' leader timeout (2 s), then one or more nullify retries (3 s each), then a view change. Measured on Linux, 25 runs of `a2_two_node_rollback`: longest stall after the restart p50 3.0 s, p90 8.2 s, max 9.7 s; with a split (at least 9 of 25), 6.3 to 9.7 s. | L-15 | **An imported key can have a second signer outside the network.** Key import is a trusted-dealer split of an existing keystore ([key-import.md](key-import.md)): the keystore, its backups and the dealer machine held the full secret, and whether the previous signer is stopped is the operator's acknowledgment, recorded by consensus but not verified. An incomplete EIP-3076 history (exported before the stop, or from the wrong signer) protects only what it contains. | Slashing of an imported key, through operator error | **Unresolved**, operational: [key-import.md](key-import.md#assumptions); the floors refuse everything at or below the imported history (E2E-IMP-1, the devnet migration) |
| L-16 | **One keyholder stopping can delay duties by a leader timeout (2 s).** A duty whose authorization falls into a view the stopped node leads waits for the 2 s leader timeout before the view is skipped. | L-17 | **An imported key's history import cannot be undone.** Floors only rise, by design, and no command lowers them. Before the activation, an interchange with high floors stops the key from signing until real duties pass them, and the key cannot be registered again. **Narrowed (P0.1):** an import takes effect only with the approvers' signatures over exactly its history, so neither an API client nor a Byzantine node can submit one; a threshold of approvers still can, and a Byzantine node relaying an approved import still bypasses the API's full-history check (consensus checks the summary, which the approvers signed). | L-18 | **Resharing needs every dealer and player, and trusts their readiness acknowledgements.** A dealing counts only if every player acknowledged it (no reveals), and a generation activates only once every new share is acknowledged: with one of them offline, a reshare cannot complete (it is aborted or fails at its deadline; the active generation keeps signing). | L-22 | **Addressed (P0): a reconfiguration needs the approvers.** It applies only with a threshold of approvers' offline signatures over the exact change and the next administrative nonce; every honest voter checks them before voting, and only an approved reconfiguration ends an epoch, so neither an API client nor a faulty leader can evict a voter or stop the network ([administration.md](administration.md)). Remaining: a threshold of compromised approver keys can still replace an honest voter by a configured follower (no time lock or governance, by design); only a configured follower can be added. | Availability, only with compromised approvers | `epochs::tests`, `admin_2`, R3-1, R3-7 |
| L-23 | **A node restored from a backup taken before a reconfiguration can equivocate in the new epoch (R3).** It replays the old epoch harmlessly (no quorum of it is left), then starts the new epoch with no journal, although the real node may already have voted in it; with no history of the new epoch yet, the missing-journal check cannot tell. The same class as L-7: never restore a consensus journal. | A Byzantine fault, tolerated within `f = 1` | [reconfiguration.md](reconfiguration.md#security-properties-and-limitations) |
| L-24 | **The time horizon trusts each node's clock (P0).** A duty is admitted, proposed and voted for only once its slot (or, for non-slashable duties, an epoch at most two ahead) has started by the node's own clock, with 2 s of leeway (4 s for voters). One node with a wrong clock refuses current duties itself or admits early ones the others refuse: availability of that node's votes only. Two or more voters with clocks far ahead, or faulty, can authorize a far-future duty and poison a validator's history; two behind stall signing. No trusted time source, consensus timestamp or NTS is used, by decision. | Liveness of duties with wrong clocks; history poisoning beyond one faulty clock | `tests/unit/eth/horizon.rs`, `horizon_1` to `horizon_3`; [ethereum-signing.md](ethereum-signing.md#time-horizon) |
| L-26 | **Fixed (P0.2): one faulty node could get a voluntary exit (or a deposit) signed.** An exit was an ordinary duty: a node gossiping it or proposing it in its own block got honest voters to authorize it (the time horizon admits exits), then honest keyholders gave partial signatures to any coordinator, so one faulty node, or any client of the loopback API, could exit any validator for good. Now an exit and a deposit are protected commands: approvals over the exact duty and the next nonce, checked by every voter; a keyholder signs such a root only if the state records it as approved, so a bare one in finalized history is never signed. Remaining: the exit's validator index is not checked against the beacon chain (approvers read it); a threshold of approvers can sign any exit (L-25) | Irreversible loss of a validator | `exits::p02_1` (a faulty leader, a faulty coordinator, the API), `storage::tests::validator::an_exit_or_a_deposit_is_signed_only_once_approved`, `admin::tests::an_exit_or_deposit_approval_binds_its_exact_signing_root` |
| L-27 | **Builder registrations are bounded by the policy, not by the operator's intent.** A registration is signed only under the approved policy (fee recipients, gas limit range, timestamp window), checked by the API, the leader, every voter, the block application and every keyholder, a retry included ([ethereum-signing.md](ethereum-signing.md#builder-registrations)). Within the policy, any API client (or a faulty node) can get a registration signed with another allowed fee recipient or gas limit, or a timestamp up to `max_future_seconds` ahead, which relays prefer until a later one; a signature returned before a policy change stays valid. Nothing limits distinct registrations per period: a faulty node can add at most 16 per block to the replicated history (the window and the per-block limit), which grows the state; there is no retention yet. Before Gloas, the policy does not cover the fee recipient of a block the beacon node builds itself (the signer sees only the header); **narrowed (Gloas):** from Gloas on a self-built payload is revealed only with an envelope, whose fee recipient the policy binds, as it binds proposer preferences'. A client with a fixed registration timestamp is refused once it is older than `max_age_seconds`. | MEV payments within the policy's fee recipients; state growth under a faulty node | `registrations::reg_1`, `reg_2`, `storage::tests::validator::registrations_follow_the_policy_in_force`, `tests/unit/eth/registration.rs`, `gloas::gl_2`, `gl_3` |
| L-28 | **Gloas: a refused or late envelope or PTC vote is lost.** Lighthouse v8.3 asks once: an envelope after publishing its self-built block, a PTC vote once per slot; it never retries either ([ethereum-signing.md](ethereum-signing.md#gloas)). A refusal (no registration policy, a fee recipient the policy does not allow, the one-per-slot rules), a timeout, or a signing pause (a restart, a reconfiguration, two nodes down) loses that block's payload (the slot's block stays, empty) or that vote. The one-per-slot rules are deliberate (two quorums of shares must not sign two different payloads or votes for a slot): a client that asks for a wrong one first loses the right one. Signing an envelope needs the block's authorization committed first, then a consensus round of its own: two rounds within the payload deadline (half a slot: 6 s on mainnet). The proposal's block root binding uses the replicated history, so an envelope for a block signed outside this cluster (before an import) is refused. Gloas's fork epoch comes with a release; a node without it refuses every duty of the Gloas epochs (fail closed). | Lost payload rewards, PTC participation | `gloas::gl_1`, `gl_2`, `gl_4`, `tests/unit/slashing.rs`, devnet `run-gloas` |
| L-25 | **Approvers are trusted, and cannot be rotated (P0).** A threshold of approver keys authorizes any protected operation, with no time lock, governance or revocation, by decision. Approver keys live with their holders (no HSM). Changing the approver set changes the cluster id and the nodes refuse to start against the recorded set; a rotation command is not implemented. A whole-network rollback (L-1) also forgets administrative nonces, so a command signed for a forgotten nonce becomes valid again. | Compromise of a threshold of approvers; operational | [administration.md](administration.md#security-properties-and-limits) |
| L-7 | **Restoring a node's consensus journal from older bytes (for example a whole data-directory backup) makes it forget its own votes.** It can then vote twice in one view (observed: `nullify` after its own `finalize`). Honest peers detect this and block it at the P2P layer for `block_duration` (1 hour), on every channel, signing included. Safety holds: consensus tolerates one equivocator, and the node still signs only what it has committed. Liveness: the node cannot catch up, coordinate or contribute partials for up to an hour; the other three continue with no spare capacity. Whether it happens depends on timing: 4 of about 32 full restores during the audit, mostly under load (it needs the node to time out a view before it fetches the certificates). Operational rule: never restore `registry-consensus` from a backup. Mitigated since (H-3): consensus resumes above the last finalization marshal durably processed, so a lost or older journal cannot repeat votes at or below it; a missing journal stops the node (H-2). Not covered: votes after that finalization, and a whole-directory restore (marshal rolled back too), which stays undetectable. | Availability of the restored node; a Byzantine fault, tolerated only within `f = 1` | `rollback::a1_full_restore_never_signs_conflict` (both outcomes), logs in `target/audit-logs/` |
| L-8 | A test process killed with SIGKILL leaves its temporary directory (and a stale port lock, reclaimed by the next run). Its nodes do exit. | Disk, tests only | `lifecycle::f1_nodes_die_with_their_test_process` |
| L-9 | A node uses ~320 MB resident at rest (a 160 MB page cache). 256 requests in flight add ~20 MB; 256 parked requests ~0.5 MB. | Sizing | `concurrency::e3_in_flight_limit` |
| L-10 | A leader that has not applied the last finalized block yet still holds that block's transactions in its mempool, so it skips the idle wait and proposes an empty block at once (the in-flight check keeps the transactions out of it). After busy blocks this adds empty blocks, and a lagging leader produces them back to back. Found while building the lag tests. | Efficiency only: more empty blocks, faster use of the block-counted retention window | `lag::*` (why the tests pause empty blocks instead of timing a freeze) |

| Conflicting activations, concurrent, through different nodes | Preserved: consensus applies the first; the other is refused everywhere, before and after restarts | Yes | same, `slashing_history_survives_a_full_restart` |
| Stale or rolled-back node and the chain identity | Preserved: it refuses until it has the activation; a duty it submits for another chain is refused when ordered | After catch-up | `stale_node_cannot_authorize_another_chain`, E2E-ETH-8 |

| A real validator client whose coordinator is stopped, behind a failover proxy | Preserved | Yes: the proxy fails over, no duty missed | devnet runs B, C and D |
| A real validator client whose coordinator crashes after consensus authorized its duty (`authorized` crash point) | Preserved: the retry on another node returns the signature of the same authorization, accepted once | Yes | devnet runs B, C and D |

The guarantees come from different places, which must not be confused:

- **Cryptographic threshold**: any 3 of 4 shares sign, 2 cannot. A share signs only what its node has
  committed.
- **Consensus BFT**: simplex with `n = 4` tolerates `f = 1` Byzantine validator. Authorization safety
  rests on it.
- **Crash tolerance**: atomic commits, replay from marshal, the height-continuity check (BUG-2).
- **Rollback resistance**: only what honest peers' finalized history provides. A rolled-back
  minority re-syncs (and stays connected if its consensus journal was kept, L-7); a rolled-back
  quorum is undetected (L-1).
- **Slashing protection**: the replicated state machine decides each validator duty by the
  specification's rules over the validator's whole history. The decision is committed with the
  authorization and checked by every keyholder. Its durability is that of the replicated state:
  it survives crashes, restarts and a minority rollback, and not a quorum rollback (L-1). The
  development API (`dev-api` builds only) has none: its nonces are caller-chosen.

